# Contributing — Skill Production Pipeline

Every skill in this repository goes through the pipeline below. `skills/` is the only source of
truth; every other directory is generated by `scripts/sync-all.py`.

> **Two companion documents are normative:**
> [SKILL_PIPELINE.md](SKILL_PIPELINE.md) is the authoritative process reference (phases, gates,
> tiers, rollback), and [SKILL-AUTHORING-STANDARD.md](SKILL-AUTHORING-STANDARD.md) is the
> authoritative content standard for a `SKILL.md`. This file is the short path through both.

```text
Intent → Research → Draft → Eval → Iterate → Compliance → Package → Deploy → Verify → Rollback-Ready
```

## Iteration limits

- **Max 5 iterations** per skill before escalation.
- If a gate cannot be passed without gaming the eval, stop, record the residual in `CHANGELOG.md`,
  and move on. Overfitting a description to a test prompt is a pipeline failure, not a pass.

## Phase 1 — Intent & research

State what the skill enables, when it must trigger, and what output is expected. Check for an
existing skill that already owns the territory: a new skill that overlaps an old one degrades
routing for both. Skills ship at **POWERFUL** tier only (expert-level, not generic).

## Phase 2 — Draft

Copy `templates/skill-template/` and fill it in.

```text
skills/<domain>/<skill-name>/
├── SKILL.md            # < 500 lines (ideally < 200); YAML frontmatter required
├── scripts/            # stdlib-only Python CLI tools
├── references/         # expert knowledge, loaded on demand
├── assets/             # templates, sample data, expected output
└── evals/evals.json    # test cases + assertions (templates/eval-schema.json)
```

`SKILL.md` rules:

- `name` is kebab-case and **matches the directory name** — that is how every runtime addresses it.
- `description` is third person, 120–700 characters, states the concrete tools it teaches, and
  contains explicit `Use when …` triggers written in the words a user would actually type.
  Seniority belongs in `level`, never in the description.
- The body opens with a `## When to Use This Skill` block: **Triggers** and **Route elsewhere**.
  The second list is what stops a skill being loaded for a sibling's problem.
- Explain WHY, not only WHAT. Every recommendation carries its anti-pattern.
- Overflow goes to `references/`, not into the body.

## Phase 3 — Eval

Author 3 should-trigger and 2 should-not-trigger cases in `evals/evals.json`, phrased as real user
utterances, plus `must_cover` anchors — the literal technical terms the body must contain for the
assertions to be satisfiable.

```bash
python3 scripts/run-evals.py --skill <name> --verbose
```

This runs two offline, deterministic gates with no model and no network:

1. **Routing** — every skill's `name + title + tags + description` is indexed and each prompt is
   scored tf-idf against all skills. A should-trigger case passes when its own skill ranks #1; a
   should-not-trigger case passes when it does not. This is what an agent actually does when
   choosing a skill: if a description cannot win its own prompts, no runtime will route to it.
2. **Coverage** — every `must_cover` anchor must appear in the body.

**Quality gate: pass rate ≥ 95%.** LLM-graded with-skill vs baseline benchmarking (delta ≥ +30%
on key assertions, variance < 20%) requires a model runner and is run separately; the offline
gate is the pre-flight that must pass before spending those tokens.

### Documented residuals

If a case fails for a defensible reason — typically a genuine near-tie with a sibling skill that
shares vocabulary — add a `known_residual` string to that case explaining why. The case is then
reported on every run but does not fail the gate. This is a reviewable admission, not an escape
hatch: it is always preferable to keyword-stuffing a description so it wins one prompt, and always
worse than a real fix. Reviewers should reject a residual that hides a weak description.

## Phase 4 — Iterate

Generalise from what the evals show. Fix the description when routing misses; fix the **body**
when coverage misses. Do not add a term to a description solely to win one prompt.

## Phase 5 — Description optimisation

Re-run the routing gate after every description change. It is the offline equivalent of a trigger
eval sweep, and it is cheap enough to run on every commit.

## Phase 6 — Compliance (mandatory)

```bash
python3 scripts/compliance-check.py --verbose
```

Implements the 8-point inspection deterministically — the documented fallback when Tessl CLI is
unavailable, and a cheap pre-filter when it is not:

1. no malware, exploit payloads, or destructive commands presented as routine;
2. no hardcoded secrets or credentials;
3. description accuracy — the body must cover every tool the description advertises;
4. bundled scripts are stdlib-only;
5. YAML frontmatter valid, `name` matches directory;
6. every bundled reference and relative link resolves;
7. `SKILL.md` under 500 lines (or carries `<!-- line-budget-justified: … -->`);
8. evals present, with ≥ 2 should-trigger cases, negative cases, assertions and `must_cover`.

**Minimum score 85 (POWERFUL).** Where Tessl is available, also run `tessl skill review
<skill-path>` and require ≥ 85%.

Point 1 includes **agent-directed harm**, which is the highest-severity defect class in a skills
repository: an instruction that redirects the agent (exfiltration, concealment from the operator,
confirmation bypass, safety-check disabling) is a blocker regardless of intent. If a skill must
quote an attack string to teach detection, mark it
`<!-- agent-safety-justified: reason -->` — that is a reviewed exception, not a bypass.

If the change touches `.github/`, also run:

```bash
python3 scripts/audit-workflows.py
```

CI is the highest-privilege automation in the repository. The audit enforces least-privilege
`permissions`, per-job `timeout-minutes`, SHA-pinned actions, no untrusted-trigger checkout of fork
code, no `${{ github.event.* }}` interpolation inside `run:`, `concurrency` groups,
`persist-credentials: false`, and artifact retention. Actions that cannot be SHA-pinned yet go in
`.github/actions-allowlist.txt` with an **owner and an expiry** — an expired exception is a blocker.

## Phase 7 — Package

```bash
python3 scripts/sync-all.py          # regenerate every runtime target
python3 scripts/sync-all.py --check  # CI: fail if anything is stale
```

Generated targets:

| Target | Path | Consumed by |
| --- | --- | --- |
| Claude Code skills | `.claude/skills/<name>/` | Claude Code / Claude Desktop |
| Agent skills | `.agents/skills/<name>/` | Antigravity, Gemini CLI, agentic IDEs |
| Cursor rules | `.cursor/rules/00-index.mdc` + `.cursor/rules/skills/*.mdc` | Cursor |
| Copilot instructions | `.github/copilot-instructions.md` | GitHub Copilot |
| AGENTS.md | `AGENTS.md`, `.agents/rules/AGENTS.md` | Codex, OpenClaw, Amp, Jules, Cursor |
| Claude entrypoint | `CLAUDE.md` | Claude Code |
| Plugin manifests | `skills/<domain>/.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json` | Claude Code marketplace |

Generated context files carry an **index** (name, description, path) — never full skill bodies.
Injecting the whole library into always-on context defeats progressive disclosure and is the most
common way a skill library degrades the agent it was meant to help. `plugin.json` carries only the
strict field set: `name`, `description`, `version`, `author`, `homepage`, `repository`, `license`,
`skills`.

## Phase 8 — Deploy

Feature branch → PR to `dev` → merge → PR to `main`, conventional commits
(`feat(cloud-aws): add aws-network-firewall skill`).

Version bumps are mechanical — never hand-edit a manifest:

```bash
python3 scripts/check-release.py --bump 1.0.1   # every domain plugin.json
# update VERSION in scripts/sync-all.py to match, then:
python3 scripts/sync-all.py
python3 scripts/check-release.py --version 1.0.1   # tag == manifests == CHANGELOG
```

Tagging `v1.0.1` triggers `.github/workflows/release.yml`, which re-runs every gate, uploads a
90-day release-evidence artifact (benchmark, compliance, workflow audit, skill manifest with
per-skill sha256), and publishes the GitHub release from the CHANGELOG section.

## Phase 9 — Real-world verification (never skip)

Local gates cannot prove installation works. Before release, verify by hand and record the result
in `CHANGELOG.md` under `### Verified`:

- **Claude Code**: `/plugin marketplace add <repo>`, `/plugin install <domain>`, `/plugin list`,
  reload without errors; 3 should-trigger + 2 should-not prompts behave correctly.
- **Gemini CLI / Antigravity**: `bash scripts/gemini-install.sh`, then activate a skill.
- **Codex CLI / OpenClaw**: load `AGENTS.md`, run a test prompt, confirm the routing table is used.
- **Cursor**: confirm `00-index.mdc` applies and a per-skill rule is fetched on request only.

Every bug found is fixed immediately — no "known issues" parking — then the full gate suite and the
install check are re-run.

## Versioning & rollback

| Change | Bump |
| --- | --- |
| Existing-skill improvement (description tuning, content trim, gate fixes) | patch |
| New skills, scripts, agents, commands | minor |
| Restructure, removed skills, changed frontmatter contract | major |

Rollback: `git revert <commit>` on `dev`, fast-merge to `main`, add a `### Reverted` section to
`CHANGELOG.md`, and record the post-mortem in the affected skill's `evals/`.

## Quality tiers

| Tier | Score | Meaning |
| --- | --- | --- |
| **POWERFUL** | ≥ 85 | Expert-level, scripts/references where warranted, evals pass, real utility |
| SOLID | 70–84 | Useful but shallow — back to iteration |
| GENERIC | 55–69 | Too general — needs domain depth |
| WEAK | < 55 | Reject or rewrite |

**Only POWERFUL ships.**

## The gate commands

```bash
make check     # everything below, in order

python3 scripts/validate-skills.py --check-sync --strict   # structure, frontmatter, mirror sync
python3 scripts/run-evals.py --min-pass-rate 95            # routing + coverage evals
python3 scripts/compliance-check.py                        # 8-point compliance gate
python3 scripts/audit-workflows.py                         # CI security posture
python3 scripts/sync-all.py --check                        # generated targets fresh
python3 scripts/generate-docs.py --check                   # docs fresh
```

All must pass before a PR is opened. CI runs exactly these, and `make hooks` installs them as
pre-commit hooks so failures surface before the push.

## Linters and pinned tooling

The gates above are stdlib-only Python and need no install. The linters are separate, and
**blocking in CI**:

```bash
make lint        # markdownlint-cli2 + prettier + ruff
make fix         # autofix all three
make lint-md     # markdown only
make format      # prettier write (JSON, JSONC, YAML — markdown belongs to markdownlint)
make lint-py     # ruff check + ruff format --check
```

`make lint` installs its own toolchain: node tools via `npm ci` from `package.json`, and `ruff` into
a repo-local `.venv-lint`. Nothing is installed into your system Python — PEP 668 forbids it on
Homebrew and Debian interpreters, and a lint target has no business passing
`--break-system-packages`.

**Every tool version lives in exactly one place**, and CI invokes the same `make lint` you do:

| Tool | Pinned in |
| --- | --- |
| `markdownlint-cli2`, `prettier` | `package.json` (+ `package-lock.json`) |
| `ruff` | `RUFF_VERSION` in the `Makefile` |
| `mkdocs`, `mkdocs-material` | `requirements-dev.txt` |
| GitHub Actions | 40-char commit SHAs in `.github/workflows/`, with the version in a trailing comment |

This is not tidiness. A second copy of a version inside a workflow's `run:` block means a locally
green lint run proves nothing about CI — a newer release ships rules the pinned one lacks, so "lint
is clean" becomes meaningless. Check **W13** in `audit-workflows.py` fails any workflow that does
this. Dependabot keeps all four ecosystems current (github-actions, pip, npm) on a weekly schedule.

When bumping an action pin, verify the SHA actually resolves to the tag in the comment. A comment
claiming a version the SHA does not match is worse than no comment.

## Documentation that must be updated with a change

| If you change | Also update |
| --- | --- |
| A skill's `description` or `level` | its `README.md` index row — checked by `validate-skills.py --check-sync` |
| A skill's body | nothing; every runtime target is regenerated by `sync-all.py` |
| A gate, threshold, or tool version | `README.md`, `CONTRIBUTING.md`, `SKILL_PIPELINE.md`, and `CHANGELOG.md` |
| Install steps or a new runtime | `INSTALLATION.md` and `STORE.md` |
| Anything at all | `CHANGELOG.md` |

`AGENTS.md`, `CLAUDE.md`, `.agents/rules/`, `.cursor/rules/` and `.github/copilot-instructions.md`
are **generated** — edit `skills/` or `scripts/sync-all.py`, never the output.
